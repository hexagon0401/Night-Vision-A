# **글로벌 인텔리전스 데이터 추출 및 온톨로지 구축 보고서: TO\_Foundry\_v6.0 대규모 업데이트 및 파싱 아키텍처**

현대의 글로벌 인텔리전스 분석 및 작전 환경에서 이기종 데이터 소스를 단일한 온톨로지(Ontology) 기반의 시각적 인터페이스로 통합하는 과정은 정보의 비대칭성을 해소하고 의사결정의 지연을 방지하는 핵심적인 역할을 수행한다. Palantir Foundry의 Map 애플리케이션은 이러한 데이터 통합의 최전선에 위치하는 시각화 엔진으로, 파편화된 공간 및 시계열 데이터를 결합하여 전 세계적인 물리적 네트워크와 동적 이벤트의 상호작용을 매핑한다.1 성공적인 데이터 온보딩과 온톨로지 구축을 위해서는 Map 애플리케이션의 렌더링 파이프라인, 공간 데이터 표준, 그리고 사용자 인터페이스 내 시각화 계층 구조를 명확히 이해해야 하며, 이를 기반으로 데이터 추출 인공지능(AI) 모델이 수행해야 할 정밀한 파싱 규격을 설계해야 한다.

본 보고서는 기존에 운용되던 TO\_Foundry\_v4.5 및 v5.0 다이렉티브의 구조적 결함과 데이터 손실 원인을 진단하고, 이를 전면적으로 개편한 TO\_Foundry\_v6.0 프레임워크를 제시한다. 기존 버전에서 발견된 치명적인 GeoJSON 이스케이프(Escape) 오류, H3 공간 인덱싱의 논리적 누락, 동적 시계열 궤적(Tracks) 데이터의 정적 처리 문제 등을 해결하기 위해 대규모 아키텍처 업데이트가 단행되었다. 더불어 Master\_Directive, Source, Relation 파일 등 핵심 통제 파일 간의 종속성을 확립하여, AI 모델이 글로벌 인텔리전스 데이터를 추출하고 Palantir Foundry로 이관할 때 발생할 수 있는 데이터 환각(Hallucination) 현상을 원천적으로 차단하는 운영 프로토콜을 규명한다.

## **Palantir Foundry Map 공간 시각화 아키텍처 및 렌더링 파이프라인**

글로벌 인텔리전스 분석을 위한 데이터 파이프라인을 구축하기 위해서는 최종 소비 계층인 Foundry Map의 기술적 요구사항과 렌더링 표준을 선행적으로 파악해야 한다. Foundry Map 애플리케이션은 평면화된 2차원 화면에 3차원 지구의 물리적 현실을 왜곡 없이 투영하기 위해 고도로 규격화된 좌표 참조 시스템(Coordinate Reference System, CRS)을 강제한다. 지도 시각화 렌더링 과정에서는 왜곡을 최소화하면서도 웹 기반의 타일 로딩 속도를 극대화할 수 있는 Web Mercator Projection (EPSG:3857)을 채택하고 있다.2 반면, 백엔드 데이터베이스에 적재되고 온톨로지로 인덱싱되는 모든 위도와 경도 좌표값은 반드시 WGS 84 (EPSG:4326) 규격을 따라야 한다.2 북미 지역의 NAD83과 같은 국지적 좌표계나 여타 로컬 CRS로 획득된 원시 정보가 WGS 84로 변환되지 않은 채 유입될 경우, 지도 상의 실제 위치와 최대 수십 킬로미터 이상의 오차가 발생할 수 있으므로, 초기 CSV 파싱 단계부터 엄격한 공간 데이터 정규화가 요구된다.3

| 특성 | 렌더링 시스템 (Rendering) | 데이터 인덱싱 시스템 (Data Indexing) |
| :---- | :---- | :---- |
| **적용 영역** | 브라우저 기반 지도 표출 및 타일 시각화 | 온톨로지 객체 저장 및 공간 검색 쿼리 |
| **좌표 참조 시스템 (CRS)** | Web Mercator Projection | WGS 84 (World Geodetic System 1984\) |
| **EPSG 코드** | EPSG:3857 | EPSG:4326 |
| **데이터 형식** | 미터(Meters) 기반의 2D 투영 | 도(Degrees) 기반의 위도 및 경도 좌표 |
| **파이프라인 통제** | MapboxGL 렌더링 엔진에서 자동 변환 수행 | Pipeline Builder 및 PySpark 통한 사전 정규화 필수 |

사용자 인터페이스 측면에서 Map 애플리케이션은 복합적인 분석을 지원하기 위해 다양한 계층(Layer)과 패널 구조를 지닌다.5 화면 좌측에는 지도의 바탕이 되는 베이스 레이어(Base Layer), 온톨로지 객체 데이터를 시각화하는 객체 레이어(Object Layer), 그리고 Map Layer Editor를 통해 사전 구성된 고품질의 공간 데이터 집합을 불러오는 오버레이 레이어(Overlay Layer)를 통합 관리하는 도구가 배치되어 있다.6 분석가는 Histogram 기능을 활용하여 속성값 및 시계열 분포를 바탕으로 화면 상의 객체를 즉각적으로 필터링할 수 있으며, 상단 툴바의 Search Around 기능을 통해 선택된 객체와 논리적으로 연결된 다른 온톨로지 객체(예: 특정 군사 기지와 연결된 보급 부대)를 지도 위로 동적으로 불러올 수 있다.1

## **온톨로지 공간 데이터의 시각적 매핑 및 논리적 제약 사항**

AI 모델이 CSV 기반의 파싱을 완벽하게 수행하기 위해서는 Palantir Foundry 온톨로지가 공간 데이터를 어떻게 해석하고(Index) 시각적으로 렌더링(Render)하는지에 대한 논리적 제약 사항을 깊이 이해해야 한다. 데이터 형태에 따라 온톨로지 내에서 부여되어야 하는 속성(Property) 타입과 제약 조건은 명확히 구분된다.7

### **점 데이터 및 벡터 기하학 데이터**

군사 기지, 개별 관측소, 타격 지점 등 독립적인 위치를 점으로 표출하기 위해서는 온톨로지 객체 내에 geopoint 속성이 정의되어야 한다.8 Foundry는 위도와 경도를 단일 문자열 형태로 저장하거나, 별도의 두 숫자형 칼럼(위도 \-90.0 \~ 90.0, 경도 \-180.0 \~ 180.0)을 기반으로 constructGeoPointV1 표현식을 통해 인덱싱하는 방식을 지원한다.9 시각적으로 이들은 고정된 핀(Pin)이나 아이콘, 혹은 원형 마커(Circle marker)로 표현되며, 속성 값 기반의 스타일링(Value-based styling)을 적용하여 특정 군사 등급에 따라 아이콘의 색상과 크기를 동적으로 변화시킬 수 있다.10 반면, 국경선, 보급로, 비행 금지 구역과 같은 복합적인 물리적 공간은 geoshape 속성에 GeoJSON 문자열의 형태로 저장되어야 한다.11 이 GeoJSON은 RFC 7946 사양을 엄격하게 준수해야 하며, 다각형(Polygon)의 경우 외곽 링이 반시계 방향(Counter-clockwise)으로 구성되어야 하고 자체 교차(Self-intersection) 현상이 발생해서는 안 된다.11 이러한 geopoint 및 geoshape 속성을 부여받은 객체는 Foundry 백엔드에서 공간 검색 기능(Bounding box 및 Polygon intersection)의 대상이 된다.11

### **등치지역도(Choropleth) 및 H3 육각형 격자 인덱싱**

광범위한 지역적 인텔리전스 분포(예: 특정 주별 폭동 발생 건수, 국가별 병력 배치 밀도)를 시각화하는 데에는 등치지역도(Choropleths)가 핵심적으로 사용된다.7 등치지역도를 구현하기 위해 AI 모델은 행정 구역의 경계 식별자(ISO 3166 등)를 직접 삽입하거나, 기하학적 형태를 가진 '지역(Region)' 객체와 정량적 수치를 포함한 '데이터' 객체 간에 다대일(Many-to-one) 관계(Relation.md 규격 참고)를 맺어주어야 한다.7 Map 상에서는 데이터 객체의 레이어를 통해 연결된 지역의 기하학적 폴리곤을 가져와 합산된 수치에 비례하는 색상 그라데이션을 렌더링하게 된다.12

또한, 대규모 데이터 포인트의 밀도 분석이나 모델링 시뮬레이션을 수행하기 위해 Uber에서 개발한 H3 공간 인덱싱 시스템이 활용된다.7 온톨로지 상에서 특정 String 속성을 H3 셀(Cell) ID로 지정하면, Foundry Map은 이를 식별하여 육각형 형태의 격자로 지도 위에 즉시 렌더링한다.7 그러나 H3 문자열 자체는 온톨로지의 공간 검색 엔진(Geospatial search engine)에 의해 인덱싱되지 않는다는 치명적인 기술적 한계가 존재한다.7 따라서 공간적 논리 연산이 필요한 인텔리전스 객체의 경우, 단순한 H3 ID 추출에 그치지 않고 해당 H3 셀의 꼭짓점 좌표를 계산하여 GeoJSON 형태의 다각형(Polygon)으로 변환한 뒤, 이를 geoshape 속성에 이중으로 적재하는 데이터 파이프라인 설계가 요구된다.7

### **시공간(Geotemporal) 궤적 및 이벤트 분석 체계**

현대의 인텔리전스 수집에서 정적인 위치 정보만큼이나 중요한 것은 대상의 동적 이동 궤적과 특정 시간대에 발생한 이벤트의 상관관계이다. Foundry Map은 시간에 따라 위치가 변화하는 함선, 항공기, 호송대 등의 경로를 가시화하기 위해 트랙(Tracks) 디스플레이를 제공한다.12 궤적 데이터를 온톨로지에 연동하기 위해서는 대상 객체가 단순한 geopoint가 아닌 Track Latitude와 Track Longitude를 나타내는 두 개의 시계열(Time Series) 속성을 보유해야 한다.14 이를 통해 Map 애플리케이션의 하단 타임라인(Timeline)을 조작할 때, 특정 시점에서의 객체 위치가 보간법(Interpolation mode)에 의해 동적으로 산출된다.14 선형 보간(Linear interpolation)은 기록된 두 좌표 사이를 매끄럽게 이어주며, 최종 확인 위치(Last known) 보간은 새로운 데이터가 들어오기 전까지 객체가 마지막 위치에 머물러 있는 것으로 처리한다. 이때 Max time gap 설정이 매우 중요한데, 두 관측 지점 사이의 시간 차이가 해당 임계값을 초과할 경우 통신 단절이나 센서 오류로 판단하여 궤적 선의 렌더링을 의도적으로 차단함으로써 분석가의 오판을 방지한다.14 더불어 특정 기간에만 유효한 이벤트 객체(예: 국지전 발생, 사이버 공격 시도)는 Event start time과 Event end time 타임스탬프 속성을 할당받아, 지도 상에서 해당 시간대에만 투명도(Opacity)가 활성화되어 나타나는 방식으로 시각화된다.12

## **레거시 아키텍처(TO\_Foundry v4.5 및 v5.0)의 구조적 결함 진단**

이러한 Foundry Map의 고도화된 시각화 요구사항을 충족시키기 위해, 과거 데이터 이관 규격이었던 TO\_Foundry\_v4.5와 v5.0이 AI 모델에 의해 광범위하게 활용되었다. 그러나 초기 다이렉티브는 평면적인 구조의 정형 테이블 데이터를 마이그레이션하는 데 초점이 맞추어져 있었기에, 복합적인 GeoJSON 객체나 시계열 기반의 궤적 데이터를 처리하는 과정에서 치명적인 파이프라인 중단(Job Failure) 및 데이터 손실 현상을 야기했다.

### **GeoJSON 이스케이프(Escape) 알고리즘의 부재와 파싱 충돌**

v4.5 및 v5.0 아키텍처의 가장 심각한 문제는 복합 다각형 데이터나 다중 선형 데이터를 CSV 칼럼에 포함시킬 때 발생하는 문자열 이스케이프 규정의 부재였다.12 GeoJSON 데이터는 필연적으로 다수의 큰따옴표(")와 중괄호({}), 그리고 때로는 띄어쓰기나 줄바꿈 문자(\\n)를 포함한다. 기존 AI 모델은 GeoJSON을 생성할 때 {"type":"Polygon", "coordinates": \[...\]} 형식의 문자열을 CSV 필드에 그대로 삽입하였다. Foundry 백엔드에서 이 CSV를 읽어 들이는 Spark의 TextDataFrameReader는 필드 구분자(Delimiter)와 문자열 인용구(Quote character)를 기준으로 칼럼을 분리하는데, 내부 큰따옴표가 이스케이프되지 않아 하나의 칼럼이 수십 개의 칼럼으로 강제 분할되는 심각한 파싱 오류를 발생시켰다.16

이로 인해 jaggedRowBehavior(들쭉날쭉한 행 처리 방식)와 parseErrorBehavior의 기본값인 THROW\_EXCEPTION이 발동하여 전체 인텔리전스 데이터 배치의 동기화가 중단되는 사태가 발생했다.16 v5.0에서 CSV\_PARSER 파라미터 튜닝이 시도되었으나, 다중 행(Multiline) 처리에 대한 지시가 명확하지 않아 줄바꿈 문자가 포함된 공간 데이터의 손실을 완전히 막지 못했다.17

### **공간 인덱싱 누락 및 H3 시각화의 논리적 모순**

v5.0 업데이트에서는 데이터 시각화의 성능 최적화를 위해 H3 인덱스 체계를 도입하여 AI 모델이 좌표 대신 H3 셀 ID(String)를 출력하도록 지시했다.7 이는 지도 화면에 벌집 모양의 격자를 빠르게 렌더링하는 데에는 성공적이었으나, 온톨로지 기반의 분석 워크플로우를 심각하게 훼손하는 결과를 낳았다. 앞서 살펴본 바와 같이, Foundry의 Search Around 및 공간 교차 쿼리(Polygon intersection queries)는 오직 geopoint와 geoshape 타입으로 정의된 속성에서만 동작한다.7 따라서 v5.0 규격에 따라 생성된 수만 건의 인텔리전스 리포트와 분석 데이터는 지도 위에는 나타나지만, 분석가가 "특정 반경 50km 이내의 위협 요소 탐색" 쿼리를 실행할 때 검색 결과에서 완전히 누락되는 유령 데이터(Ghost Data) 현상을 유발했다.2

### **시계열 궤적(Tracks) 모델링의 정적 처리 한계**

이동하는 전술 자산(함대, 병력, 수송기 등)을 다루는 글로벌 인텔리전스 도메인에서 v4.5와 v5.0은 심각한 정보의 단편화를 초래했다. 기존 AI 프롬프트는 대상 객체의 위치를 단일한 '현재 위치(Current Location)'라는 정적 스키마로 덮어쓰도록 강제하거나, 매 분마다 발생하는 위치 데이터를 완전히 새로운 개별 객체 행(Row)으로 생성하도록 지시했다.12 첫 번째 방식은 객체의 이동 경로와 과거 작전 내역을 영구히 소실시켰고, 두 번째 방식은 동일한 함선 하나가 지도상에 수천 개의 파편화된 점으로 나타나 시각적 혼란을 가중시켰다. Foundry Map의 궤적(Tracks) 기능이 요구하는 단일 객체 ID와 시계열 배열(Time Series Arrays)의 결합 구조를 전혀 이해하지 못한 아키텍처 결함이었다.18

| 아키텍처 특성 | TO\_Foundry\_v4.5 | TO\_Foundry\_v5.0 | 구조적 결함 및 한계점 |
| :---- | :---- | :---- | :---- |
| **공간 데이터 포맷** | 단일 위도/경도 칼럼 | GeoJSON 및 H3 ID 추가 | CSV 내부의 큰따옴표 이스케이프 미처리로 인한 Spark THROW\_EXCEPTION 파싱 에러 빈발 |
| **공간 검색(Indexing)** | geopoint 변환 매핑 | H3 String 위주의 매핑 | H3 데이터가 시각적으로는 렌더링되나, Bounding Box 등의 공간 검색(Search Around)에서 누락 |
| **시계열 궤적(Tracks)** | 정적 좌표 덮어쓰기 적용 | 개별 객체 분리 생성 방식으로 회피 | 단일 객체의 시계열 보간(Interpolation) 불가 및 Timeline 기능을 활용한 궤적 시각화 완전 실패 |

## **인텔리전스 추출 운영 프레임워크의 유기적 통제 체계**

새로운 다이렉티브를 설계하기 이전에, AI 모델이 작업을 수행할 때 반드시 준수해야 하는 네 가지 핵심 통제 파일(Master\_Directive.md, Source.md, Relation.md, TO\_Foundry.md)의 유기적 종속성을 확립해야 한다. 이 파일들은 단순한 지침서가 아니라 글로벌 인텔리전스 데이터를 군사/산업적 목적으로 정제하기 위한 프로그래매틱 파이프라인의 청사진이다.

1. **Master\_Directive.md (명령 통제소):** AI 에이전트가 가장 먼저 참조해야 하는 핵심 지시서이다. 사용자의 프롬프트가 주어지면 이 파일을 통해 수집해야 할 정보의 도메인이 어떤 케이스(CASE A\~K)에 해당하는지를 식별한다. 글로벌 전역(미국, 러시아, 이란, NATO 등)의 모든 지리적, 군사적, 경제적 이슈가 유효한 분석 대상이 된다.  
2. **Source.md (신뢰도 검증 및 OSINT 폴백):** 인텔리전스의 출처를 식별하는 레지스트리이다. G(정부), T(기술), U(분류 불가), S(신호정보), Q(정량데이터), W(오픈소스), M(군사) 등의 ID와 계층(Tier)을 제공한다. 특히 사용자의 주제가 사전 등록된 소스 목록에 없을 경우, AI 모델은 임의로 응답을 거부해서는 안 된다. 대신 자동적으로 **CASE J (OSINT Fallback)** 프로토콜을 발동시켜 W-Tier 소스 데이터를 기반으로 인텔리전스를 구축해야 한다.  
3. **Relation.md (도메인 온톨로지 스키마):** 수집된 데이터를 온톨로지로 변환하기 위해 DOMAIN-0에서 DOMAIN-11까지의 스키마와 데이터베이스 간의 관계성(Relational mapping)을 정의한다.  
4. **환각 방지(Hallucination Prevention) 및 Output Protocol:** 본 운영 규칙에서 말하는 '환각 방지'란 미등록 소스의 주제를 거부하는 것이 아니라, 데이터를 절대로 조작(Fabricate)하지 않는 것을 의미한다. 특히 위도와 경도 같은 공간 데이터의 경우, AI 모델이 메모리나 추측에 의존하여 좌표를 생성해서는 안 되며, 정확한 좌표를 산출할 수 없을 때는 공간 칼럼을 비워두고 반드시 pending\_verification 플래그를 표기해야 한다. 모든 분석의 내부 처리 과정은 영어로 진행하여 스키마의 무결성을 유지하되, 최종 사용자에게 제공되는 내러티브 및 분석 보고서는 한국어로 출력된다. 최종 산출된 CSV 데이터는 /Compass/GlobalIntel/\[domain\]// 경로로 명확히 적재되어야 한다.

## **TO\_Foundry\_v6.0: AI 모델 파싱 및 스키마 생성 마스터 다이렉티브**

기존 버전들의 모든 아키텍처 결함을 근본적으로 해결하고, Palantir Foundry Map의 최신 렌더링 파이프라인과 완벽히 동기화되기 위해 **TO\_Foundry\_v6.0 (Major Architecture Update)** 버전을 아래와 같이 선언한다. 본 섹션은 AI 모델이 내부 논리 프로세서에서 직접 읽고 적용해야 하는 '실행 코드 및 파싱 매뉴얼'의 역할을 수행하므로, 프로그래매틱 처리의 일관성을 확보하고 프롬프트 명령어 구조와의 충돌을 방지하기 위해 엄격한 영문 규격(English Specification)으로 기술된다. 이 다이렉티브는 AI가 데이터 추출 후 Foundry에 적합한 CSV를 생성할 때 무결성을 보장하는 가장 강력한 규칙이다.

### ---

**TO\_Foundry\_v6.0 : Master Ingestion & Geospatial Schema Rules**

**1\. ARCHITECTURAL OVERVIEW & COMPLIANCE**

This directive completely deprecates TO\_Foundry v4.5 and v5.0. It introduces critical remediations for GeoJSON CSV escaping errors, H3 spatial indexing limitations, and the fundamental absence of geotemporal track modeling. You, the AI agent, must apply these rules rigorously when formatting extracted global intelligence data into CSV outputs. Total adherence to the WGS 84 (EPSG:4326) coordinate reference system is mandatory for all spatial columns. Your CSV structures must align perfectly with the schemas defined in Relation.md while utilizing the source verifications from Source.md.

**2\. SPATIAL DATA FORMATTING & ESCAPING PROTOCOLS**

* **Rule 2.1: Geopoint Handling (Static Coordinates)**  
  When identifying the static location of an entity (e.g., a military installation, port, or factory), generate two distinct columns: latitude and longitude. Both must be Double values (-90.0 to 90.0 and \-180.0 to 180.0, respectively).  
  *Hallucination Prevention Override:* If OSINT sources (Case J) or specified tiers do not provide exact verifiable coordinates, YOU MUST NOT generate them from internal memory approximations. Leave latitude and longitude fields entirely empty (NULL) and explicitly append "pending\_verification" to the geo\_status column. The Foundry Pipeline Builder will handle the NULL cast safely.  
* **Rule 2.2: Geoshape and GeoJSON Handling (Boundaries and Areas)**  
  For complex territorial data (e.g., maritime exclusion zones, combat frontlines), use the geoshape\_geojson column. The geometry must be valid RFC 7946 GeoJSON.  
  *CRITICAL CSV ESCAPING REQUIREMENT:* To prevent Spark TextDataFrameReader THROW\_EXCEPTION failures (a flaw in v5.0), you must double-escape every internal quotation mark within the GeoJSON string, and enclose the entire string in bounding quotes.  
  * *Invalid Output:* {"type": "Polygon", "coordinates": \[...\]}  
  * *Valid Output (v6.0 Mandatory):* "{""type"": ""Polygon"", ""coordinates"": \[...\]}"  
* **Rule 2.3: H3 Hexagon Dual-Indexing**  
  When generating data for density analysis or area coverage using Uber's H3 spatial index, outputting merely the H3 string is insufficient because Foundry's Search Around engine cannot index raw H3 IDs for bounding box queries. You must generate TWO columns:  
  1. h3\_cell\_id: The raw H3 string (e.g., "82f25ffffffffff") for rapid map rendering.  
  2. h3\_geojson: A converted GeoJSON Polygon representing the exact vertices of that specific H3 hex cell, escaped strictly per Rule 2.2. This ensures full spatial indexing compatibility.

**3\. GEOTEMPORAL TRACKS (MOVING OBJECTS) MODELING**

To resolve the static fragmentation of tracking data (such as naval vessel movements or troop deployments), the CSV output must be formatted to feed directly into Foundry's Time Series properties, enabling the Map application's Timeline and "Max time gap" track interpolation.

* **Temporal Precision:** Every row representing a movement update must include a timestamp column formatted strictly in ISO 8601 (YYYY-MM-DDTHH:MM:SSZ).  
* **Track Schema:** Output distinct updates using object\_id as the primary grouping key, paired with track\_latitude and track\_longitude. Do not attempt to pre-merge these points into a static LineString GeoJSON. Foundry requires discrete rows to apply visual opacity fading and interpolation (Linear or Last known) correctly across the temporal axis.

**4\. SPARK CSV DATAFRAMEREADER SCHEMA DEFINITION**

When instructed to provide the schema configuration for the Foundry ingestion pipeline, you must output the following JSON block. This configuration forces Spark to safely parse the deeply nested and escaped GeoJSON multi-line structures generated in Rule 2.2 without crashing the data build.

JSON

"dataFrameReaderClass": "com.palantir.foundry.spark.input.TextDataFrameReader",  
"customMetadata": {  
  "textParserParams": {  
    "parser": "MULTILINE\_CSV\_PARSER",  
    "charsetName": "UTF-8",  
    "fieldDelimiter": ",",  
    "recordDelimiter": "\\n",  
    "quoteCharacter": "\\"",  
    "escapeCharacter": "\\"",  
    "jaggedRowBehavior": "DROP\_ROW",  
    "parseErrorBehavior": "THROW\_EXCEPTION",  
    "skipLines": 1  
  }  
}

*Note:* The transition from CSV\_PARSER to MULTILINE\_CSV\_PARSER alongside explicitly defining the escapeCharacter as \\" completely rectifies the legacy jagged row anomalies. jaggedRowBehavior is set to DROP\_ROW to ensure the survival of the pipeline if corrupted OSINT narrative fields exceed column limits.

**5\. PYSPARK TRANSFORMATION INSTRUCTIONS (GEOSPATIAL TOOLS)**

If raw files are ingested in non-WGS84 projections (e.g., local Shapefiles), provide the following PySpark transformation logic leveraging Palantir's geospatial\_tools decorators. This guarantees absolute compliance with EPSG:4326 before the data hits the Ontology mapping layer.

Python

from transforms.api import transform\_df, Input, Output  
from geospatial\_tools import geospatial  
from geospatial\_tools.functions import clean\_geometry, geojson\_to\_geohash, centroid

@geospatial()  
@transform\_df(  
    Output('/Compass/GlobalIntel/Domain\_Output/clean\_wgs84\_geo'),  
    raw\_df=Input('/Compass/GlobalIntel/Domain\_Input/raw\_geo\_ingest')  
)  
def process\_spatial\_data(raw\_df):  
    \# Rule: Strict conversion of any geometry to WGS 84 (EPSG:4326)  
    normalized\_df \= raw\_df.withColumn(  
        'geoshape\_geojson',   
        clean\_geometry('raw\_geometry', 'EPSG:4326', output\_format='geojson')  
    )  
      
    \# Rule: Generate a Geohash fallback column for rapid point-based heatmap clustering  
    final\_df \= normalized\_df.withColumn(  
        'centroid\_geohash',   
        geojson\_to\_geohash(centroid('geoshape\_geojson'))  
    )  
      
    return final\_df

**6\. MANDATORY OUTPUT PROTOCOL INVOCATION**

Every final intelligence extraction payload must end with the generation of the CSV block. The CSV must feature the columns: source\_id (e.g., W-742), confidence\_level (e.g., 0.85), geo\_status, and the relevant spatial columns (latitude, longitude, geoshape\_geojson). Do not output explanations of the CSV format to the final user unless explicitly queried; focus the narrative analysis in Korean, and provide the precise CSV code block required for Foundry ingestion.

**데이터 무결성 확보 및 파이프라인 최적화 (Data Lineage & Pipeline Builder)**

새롭게 도입된 TO\_Foundry\_v6.0 아키텍처는 AI 모델이 생성하는 정형 데이터의 품질을 보장할 뿐만 아니라, Foundry 내부의 시각적 로직 도구들과 유기적으로 결합하여 최종적인 파이프라인 최적화를 달성한다. 이전 워크플로우에서는 복잡한 공간 데이터 정규화를 위해 파이썬(Python) 기반의 geospatial\_tools 라이브러리와 Apache Sedona를 활용한 코드 저장소(Code Repositories) 기반의 변환 방식이 필수적이었다.4 그러나 최근 Foundry의 아키텍처 진화에 따라, Pipeline Builder 내에 논리적 타입(Logical Types) 개념이 도입되면서 데이터 무결성 검증 프로세스가 비약적으로 단축되었다.19

TO\_Foundry\_v6.0 규격을 준수하여 완벽하게 이스케이프 처리된 GeoJSON 문자열이 CSV 형태로 유입되면, 별도의 PySpark 스크립트 작성 없이 Pipeline Builder의 Logical Type Cast 표현식을 사용하여 데이터를 즉시 Geometry 또는 GeoPoint 타입으로 전환할 수 있다.19 만약 입력된 좌표가 위도 \-90\~90도, 경도 \-180\~180도의 유효 범위를 벗어나거나 GeoJSON 규격을 위반할 경우, 시스템은 해당 필드를 안전하게 Null 값으로 무효화(Nullify)하여 온톨로지 전체의 인덱싱이 오염되는 것을 방지한다.19

또한, AI 모델이 pending\_verification 플래그를 부착한 채로 좌표를 비워둔 불확실한 인텔리전스 데이터는 Data Lineage 상에서 즉각적으로 추적이 가능하다.20 분석가는 Lineage 그래프를 통해 해당 데이터가 어떤 Source ID와 T/U/S/Q/W/M 티어(Tier)에서 유입되었는지 역추적할 수 있으며, Case J(OSINT Fallback)로 수집된 W-Tier 정보의 신뢰도를 수동으로 검증한 후 Foundry Rules를 적용하여 지도 시각화 레이어에 안전하게 반영할 수 있다. 이러한 일련의 설계 철학은 시각화 엔진의 렌더링 성능을 극대화할 뿐만 아니라, 조작되거나 추측된 공간 데이터(Hallucinated Coordinates)가 군사적, 전략적 의사결정에 개입하는 것을 원천적으로 봉쇄하는 무결성 방어 체계로 기능한다.

궁극적으로 TO\_Foundry\_v6.0 체계는 Palantir Foundry Map 애플리케이션의 본질인 시간적(Temporal) 맥락과 공간적(Spatial) 실재의 융합을 기술적으로 담보하며, 어떠한 전역적 위기 상황이나 파편화된 데이터 소스 환경 속에서도 가장 신뢰할 수 있는 글로벌 인텔리전스 시각화 인프라를 제공할 것이다.
